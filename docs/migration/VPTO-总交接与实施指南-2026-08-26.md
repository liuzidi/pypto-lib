### 1.2 编译后端选择与 .pto 落盘（关键机制）
- `python/pypto/ir/compile.py::_backend_type_for_platform`：platform `"a5"/"a5sim"` → `BackendType.Ascend950`；其 `GetExtraPtoasFlags()` → `{"--pto-arch", "a5"}`。注意它**不**决定 emitc/vpto——ptoas 默认 emitc，VPTO 靠 ptoas 侧 `--pto-backend=vpto` 切换。
- **.pto 必然落盘**：`python/pypto/backend/pto_backend.py:1213-1215` 在执行 ptoas 前把 IR 写到 `output_dir/ptoas/<unit_name>.pto`。→ "Python→.pto" 零成本，不需要改 pypto。
- `pto_backend.py` 另有 `skip_ptoas=True` 模式（约 1496 行）可只产 MLIR 不调 ptoas（相关旗标：`--pto-level=level3`、`--enable-insert-sync`）。
- `golden/runner.py::run_jit`（1370 行）签名：`run_jit(fn, specs, golden_fn=None, golden_data=None, compile_cfg=None, runtime_cfg=None, rtol=1e-5, atol=1e-5, compare_fn=None, compile_only=False, runtime_dir=None, save_data=False)`。`compile_only=True` 只编译不上板；`runtime_dir` 复用已有 build_output 目录。EmitC 黄金对照流程：compile → golden → NPU → compare。

## 4. 历史调查（3-4 周文档）核心结论

### 4.1 5 层墙（Route1 vs Route2 差异）
| 层 | Route1 (EmitC) | Route2 (VPTO) |
|---|---|---|
| L1 | FRAA | CUBE magic |
| L2 | 外层 .text 已链接 | 未链接 |
| L3 | `kernel_entry(int64_t* args)` ABI | 扁平 `__gm__` 指针 ABI |
| L4 | resident-kernel + AICPU 调度器 | 一次性执行 |
| L5 | rtRegisterAllKernel / rtKernelLaunchWithHandleV2 | .so dlopen + rtFunctionRegister + rtKernelLaunchWithFlagV2 |

### 4.2 两条启动路径的裁决
- **Option 1''（offset-0 launch）**：旧 507015（`ACL_ERROR_RT_AICORE_EXCEPTION`）的坑源，已放弃。
- **Option 2（.so + 扁平指针 + 名字查找 + bisheng `<<<>>>`）**：**确定性可行** —— skill 实现的就是这条，已在 39 上跑通 3 个模块算子。

### 4.3 原 C1-C4 分解（3-5 周估计）
- **C1** 编译路径 fatobj→.so（bisheng 链）≈1 周 —— **已完成**（skill / vpto_runner 已验证）
- **C2** 在 simpler C++ 加第二套启动 ABI（~100 行 flag-gated）—— 未做（本轮不需要）
- **C3** 参数打包扁平指针 —— 已内嵌在 skill 的 launch/main 模板里
- **C4** 模块编排器（复用 `_get_dep_graph`）—— 未做（本轮不需要）

### 4.4 为什么现在缩到 1-2 天
1. 后段（C1）已验证：skill 在 39 上把 3 个模块算子跑成 bit-exact；
2. 前段免费：pypto 编译必落 .pto；
3. 用户本轮只要"一个产物上板，不求精度"，**不需要** simpler 模块级编排（C2/C4 是为那个目标服务的）。

## 6. 方案思考（为什么这样做）

### 6.1 目标架构
```
models/deepseek_v4_pro/xxx.py
   │ pypto run_jit/compile（compile_only 只编译；.pto 必落盘）
   ▼
 build_output/<prog>/ptoas/<unit>.pto      ← 桥的输入（已存在）
   │ 桥（40-80 行）：① 两个 sed 补 attrs ② 调 vpto_runner / skill 逻辑
   ▼
 ptoas --pto-backend=vpto → fatobj .o → bisheng --cce-fatobj-link -shared → .so → host bin
   │ task-submit --device 0
   ▼
 上板执行
   │ 对比：复用模型自带 golden_fn（torch CPU，跑在板内任务里）
   ▼
 结果（不求 bit-exact，只求跑通；能精确更好）
```

### 6.2 桥的两个 sed（proven-working，来自 SKILL.md）
1. **module attrs**：加 `pto.kernel_kind = #pto.kernel_kind<cube|vector>`（按源 .pto 内容自动判定类型；实现在 `lib/setup_vpto.py::detect_kernel_kind`，`vpto_run.py:397` 调用）。
2. **func attrs**：`attributes {pto.kernel_kind` → `attributes {pto.kernel, pto.kernel_kind`（`pto.kernel` 是触发 kernel body 代码生成的关键）。

**关键教训**：`--enable-op-fusion` 关掉会静默产出只有 `cceModuleCtor` + `__cce_ptc_wrapper`、无 kernel 符号的**空 fatobj** —— 这就是 A5 上"VPTO 无法 lower pypto EmitC tile dialect"误判的真正原因（SKILL.md 已纠正；rmsnorm vector 与 qwen3_decode_incore_1 cube 都验证过能出真 kernel 并在 A5 npu:0 执行）。

- ptoas 参数（baseline route）：`--pto-arch=a5 --pto-level=level3 --pto-backend=vpto --enable-tile-op-expand --enable-insert-sync --enable-op-fusion`
- bisheng：`--cce-fatobj-link -shared` 链接 fatobj + `launch.cpp`（`func<<<1, nullptr, stream>>>`）→ .so；CANN module load（`rtRegisterGlobals` / `__cce_rtKernelLaunchWithFlagV2`）。**不需要改 simpler runtime**——skill 用自带 main.cpp 完全绕过 simpler 的 InCore 路径。
- 另有 `--route vmi-membar-vfoff`（VMI fusion + membar + 7 个 bisheng -mllvm VF-fusion-off 选项 + `-cce-vf-stack-size=0x10000` 防栈溢出），调优用；默认 baseline。

### 6.3 方案对比
| 方案 | 成本 | 本轮是否需要 |
|---|---|---|
| A. 走 skill / vpto_runner 独立 host 链（本文 P1-P3）| 1-2 天 | ✅ 是（用户本轮验收口径）|
| B. 改 simpler C++（C2）使其能跑 VPTO 产物 | ~2-3 周 | ❌ 非本轮；未来做"模块级编排 + 完整 golden 复用"时再启，配合 C4 |
| C. 在 pypto 后端加 VPTO 支持（改 compile 链）| 大 | ❌ 不需要：ptoas 已支持 VPTO 输出 |

### 6.4 "不求精度"的验收口径
只要 kernel 在板上执行完、无 507015、host 侧对比流程跑通即算 PASS；bit-exact 是加分项（P3 名单优先挑历史 bit-exact 的算子）。
